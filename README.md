# 수치 감사

**협업 공간에 쌓인 글에서 수치가 서로 맞는지, 그 숫자가 어디서 왔는지 감사하고, 걸린 것을 업무로 되돌린다.**

공지 초안에 `250ms`가 올라간다. 그런데 스프린트 어느 글에도 그 숫자를 어떻게 쟀는지가 없다.
회의록은 「1,200여 개」라 하고 QA 글은 「1,284 케이스」라 한다. 3주차 글의 「42개」는 케이스가 아니라 파일 수다.
글은 쌓이고 숫자는 옮겨 다니는데, 옮겨 다닌 경로는 아무 데도 안 적힌다.

```
플로우 글·댓글 → 정제 → 추출 → 게이트 → 판정 → 업무로 되돌리기
                블록 복원  Gemini   코드     코드     플로우 API
```

## 스키마가 강제하던 것을, 글은 강제하지 않는다

탄소 배출량을 계산하는 SaaS 를 만들었다. 거기서 배출계수는 값 하나로 서지 않는다.
어느 상용 DB 의 몇 번째 판인지, 할당 방법론이 cut-off 인지 APOS 인지 consequential 인지,
어느 지역 것인지가 같이 있어야 성립한다. 그래서 **스키마가 그 축들을 컬럼으로 강제한다.**
계수를 흐름에 붙일 때는 데이터 품질 5축을 값 옆에 같이 저장한다.

그 축은 DB 안에서만 강제된다. 문서로 나오면 빠진다.

계수 버전 목록 조회가 실제로는 두 축으로 걸려 있었는데 문서에는 한 축만 적혀 있었다.
「왜 이 버전은 목록에 안 뜨는가」의 답이 어디에도 없었다. 정정하면서 만진 파일이 여덟이다 —
GraphQL 설명문, API 명세 HTML, 프론트 핸드오프, 서비스 주석. 한 번에 안 끝나서 다음 날 남은 문서를 또 고쳤다.

값 자체가 갈린 것도 있다. 방법론 명세 문서는 영향평가 지표가 **25개**라 했고 실제 DB 에는 **12개**였다.
원인은 지금도 안 적혀 있고 「확인 필요」에 미해결로 남아 있다.

그쪽은 스키마와 CI 가 지킬 수 있는 자리였다. 협업 공간에 쌓이는 글은 그렇지 않다.
「250ms 로 개선」이라고 쓸 때 무엇을 어떻게 쟀는지를 같이 적으라고 강제하는 것이 없고,
안 적혀도 아무 일이 일어나지 않는다.

## 모델을 쓰는데, 모델을 믿지 않는다

수치를 뽑는 건 모델이다. 모델은 가끔 없는 것을 만든다.
그래서 뽑을 때 **「원문 어느 구절에서 봤는지」를 같이 내게 하고, 코드가 그 구절을 원문에서 직접 찾는다.**
모델에게 「너 확실해?」라고 되묻는 방법도 있지만, 같은 모델에게 한 번 더 묻는 것이라 새 정보가 없다.

| # | 조건 | 막는 것 |
|---|---|---|
| ① | `quote` 가 **그 문서** 원문에 실재 | 다른 글의 문장을 끌어오는 것 · 배치의 오귀속 |
| ② | `valueText` 가 `quote` 안에 실재 | 인용은 진짜인데 값은 지어낸 것 |
| ③ | 값 주변 문맥이 3자 이상 | 값만 인용하면 어느 문서 것인지 못 가린다 |

대조는 2단이다. 1차는 공백을 지우고 포함을 보고, 실패하면 2차로 문장부호를 정규화한다.
**2차 통과를 따로 센다.** 느슨한 규칙으로 몇 건이 통과했는지가 게이트의 실제 강도다.

라운드 1~4 통틀어 2차 통과는 **0건**이다. 느슨한 규칙이 필요했다는 증거가 아직 없다.
게이트가 실제로 무언가를 버린 것도 라운드 4에서가 처음이다 — 모델이 앞줄의 불릿 `- ` 를 끌어다
`"- 요청당 쿼리가 47회 나갑니다."` 라는 원문에 없는 문장을 만들었다. `47회` 자체는 그 글에 있다.
**참인 주장이 거짓 인용 때문에 버려졌다.** 게이트가 보는 것은 수치의 진위가 아니라 인용의 실재다.

## 판정도 코드가 한다

「이 숫자가 근거 있나」를 모델에게 물으면 그건 또 모델을 믿는 것이다. 코드가 볼 수 있는 사실로만 가른다.

**견줄 대상을 고르는 일까지는 모델이 한다.** 같은 지표끼리 묶는 게 그것이다 — 코드로 해 봤고 졌다(라운드 1).
모델이 고른 뒤, **「같다/다르다」로 떨어뜨리는 마지막 한 걸음만 코드가 맡는다.**

여기서 말하는 **근거는 「어떻게 쟀는지」**다 — `스테이징 · 동시 10 · 캐시 미적용`, `캐시 워밍 후 3회 평균` 같은 것.
추출할 때 `method` 로 따로 받고, 원문에 안 적혀 있으면 반드시 빈 문자열이다.

**1차는 같은 지표 그룹 안에서 본다.** 측정 방법이 적힌 값이 있는데 이 값만 없으면 걸린다.
같은 값이 다른 글에서 방법과 함께 나오면 걸리지 않고, 아무도 방법을 안 적은 지표는 통째로 그냥 둔다.

**2차는 그룹 밖으로 나간다.** 글쓴이가 수식어를 빼고 쓰면(`p95 응답시간` → `검색 응답`) 모델은 다른 지표로 가르고,
그러면 그룹 안에 견줄 상대가 사라진다. 상위 모델(`gemini-3.6-flash`)로 묶어도 갈렸다.
그때만 **단위가 같은 값들**과 견준다. 단위축 묶기는 라운드 1에서 이미 졌던 방법이다(`ms` 라는 이유로 응답시간과 타임아웃이 한 그룹이 됐다).
그래서 묶는 데 쓰지 않고 「견줄 상대가 있나」에만 쓰고, 화면에 **「그룹 밖 대조」라고 등급을 적는다.**

**조건이 다른 값은 견주지 않는다.** `320ms(스테이징 · 동시 10 · 캐시 미적용)` 와 `280ms(캐시 워밍 후 3회 평균)` 는
값이 다른 게 아니라 **애초에 견줄 수 없는 두 숫자**다. 그래서 지표 그룹 안을 **조건별로 한 번 더 나누고**, 같은 조건끼리만 견준다.

조건이 같은지는 문자열로 못 가른다 — `캐시 미적용` 과 `캐시 없이` 는 같은 조건인데 글자가 다르다.
완전 일치는 놓치고, 유사도는 임계값을 감으로 정해야 한다(인용 길이 `6자` 로 한 번 데인 자리다).
그래서 **묶는 것은 모델이 하고, 갈렸는지 여부만 코드가 본다.** 지표 묶기와 같은 자리다.
모델이 낸 것은 조건 설명문이 아니라 **claimId 묶음**이라, 참조 게이트를 세 번째로 그대로 건다.

**조건이 갈렸다고 지우지는 않는다.** 화면과 업무 본문에 남기고 「조건이 달라 견주지 않았다」고 적는다 —
모델이 잘못 갈랐으면 사람이 거기서 뒤집는다.

판정은 **「숫자가 틀렸다」가 아니라 「감사한 글에서 근거를 못 찾았다」**까지만 말한다.

## 왜 수치에서 멈췄나

출발은 더 위였다 — 앞 절의 그 드리프트 전부다.
**ADR 과 그 뒤에 바뀐 설계, 같은 문서의 여러 판, ERD 와 인터페이스 명세.**
연관 문서가 서로 어긋난 채 굳는 것이 원래 보려던 것이다.

거기서 수치만 잘라냈다. 자른 기준은 하나다.

> **견줄 대상을 고르는 건 모델에게 넘긴다.
> 견준 결과를 「같다/다르다」로 떨어뜨리는 자리에는 코드가 설 수 있어야 한다.**

수치는 그 자리에 코드가 선다. `320` 과 `280` 이 다른지는 코드가 말한다.
「이 ADR 이 저 ERD 와 모순인가」는 그렇지 않다 — 마지막 한 걸음까지 모델이 밟아야 한다.
그러면 인용은 여전히 검산되는데 **정작 판정은 아무도 되짚지 않는다.** 게이트는 남고 지킬 것이 없어진다.

같은 자로 재면 문서 정합성에도 넘어오는 것이 있다. 필드 이름·타입·엔드포인트 경로처럼
**값이 자유 텍스트가 아니라 식별자인 주장**은 수치와 성질이 같다.
넓히는 길은 [다음에 손댈 곳](#다음에-손댈-곳)에 적어 뒀다.

## 고칠 수 없어서 사람에게 넘긴다

플로우 API에 **글 본문 수정이 없다.** 틀린 숫자를 찾아도 도구가 고칠 수 없다.
그리고 **삭제가 전부 없다**(프로젝트·글·댓글). 쓰기는 되돌릴 수 없다.

두 사실이 UX를 정했다. 미리보기가 기본값이고, 도구가 먼저 쓰지 않는다.
대신 감사 결과를 플로우의 업무 모델로 되돌린다 — 지표 그룹 하나가 업무 하나, 어긋난 값 하나가 하위업무 하나,
그 수치를 쓴 사람이 담당자, 판정 종류가 우선순위, 확인 요청이 상태다. 등록 버튼은 사람이 누른다.

여기서 안 하는 것도 적어 둔다. 목표 달성 여부를 판정하지 않는다(지표의 좋은 방향이 원문에 없다).
「2배 빨라졌다」류 파생 수치를 검산하지 않는다(근거가 글 밖에 있다).
어느 값이 맞는지 고르지 않는다 — 고칠 API도 없고 고를 근거도 없다.

## 한도가 구조를 정했다

Gemini 무료 티어는 **모델당 하루 20회**다. 문서당 1회로 부르면 하루 20문서가 천장이고, 실제 프로젝트방은 글이 수백 건이다.
그래서 배치로 넣는다. 배치는 새 실패 모드를 만든다 — 모델이 주장을 엉뚱한 문서에 붙이는 **오귀속**이다.
인용 게이트가 그대로 잡는다. `quote` 를 **그 `docId` 의 원문**에 대고 보기 때문이다.

입력 상한은 1,048,576 토큰이고 출력 상한은 65,536 토큰이라, 배치가 커지면 출력이 먼저 찬다.
배치 예산은 문서당 출력 실측에 안전계수 2를 곱해 **배치당 100문서 · 입력 200,000토큰**으로 잡았다.
`finishReason` 이 `MAX_TOKENS` 면 잘린 것이므로 조용히 넘기지 않고 배치를 쪼갠다.

일일 소진과 분당 제한은 다르다. 서버는 일일 소진에도 `retryDelay: 46s` 를 준다.
그 말을 믿고 5회 재시도해서 5분을 태웠다. 지금은 `quotaId` 에 `PerDay` 가 있으면 기다리지 않고 다음 모델로 내려간다.

### 모델은 별칭이 아니라 버전으로 고정한다

같은 입력·같은 채점에서 `gemini-flash-lite-latest` 는 **31건**, `gemini-3.1-flash-lite` 는 **19건**을 뽑았다.
별칭은 언제든 다른 모델로 해석된다. 하마터면 이 차이를 「노이즈가 추출을 깎았다」로 쓸 뻔했다.
결과 JSON에 `usage.byModel` 을 항상 남기고, 화면에도 그대로 적는다.

## 붙여 보고 안 것

문서만 읽어서는 안 나오는 것들이다. 전부 실제 호출로 확인했다.

| | |
|---|---|
| **실패도 HTTP 200 으로 온다** | `res.ok` 로 판정하면 조용히 통과한다. 응답 봉투의 `success` 를 본다 |
| **`outContent` 이 블록 경계를 지운다** | 에디터 글 3건·이음매 22곳 중 3곳이 구분자 없이 붙었다(`"초대합니다!◾ 일시 :"`). 붙은 문자열은 **원문에 실재하므로 게이트가 못 잡는다** → `htmlContent` 를 블록 단위로 푼다 |
| **업무 상태가 두 축이다** | 생성 body 의 `status` 와 화면에 보이는 상태 컬럼(`optionSrno`)이 별개다. 컬럼은 생성 후 PATCH 해야 바뀐다 |
| **상태를 바꾸면 시스템 댓글이 남는다** | `"상태를 '대기'에서 '완료'으로 변경하였습니다."` 그대로 두면 감사 입력이 오염된다 → `systemCode` 가 빈 것만 사람 댓글로 센다 |
| **담당자는 지정할 수 있다** | 전역 `GET /user/search/employees` 가 빈 배열이라 한때 「불가능」이라 적었다. 봐야 할 곳은 `GET /user/projects/{id}/participants` 였다 |
| **`connectUrl` 이 내부 호스트로 온다** | `internal-private-prod-api-alb-….elb.amazonaws.com`. 공개 호스트로 바꿔 열면 오류 페이지로 튄다 → 쓰지 않는다 |
| `GET /user/projects` | `cursor` 만 받는다. `pageSize` 를 붙이면 `VALIDATION_ERROR` |

한 가지 더. 등록한 업무 본문에는 인용이 그대로 들어 있어서, 다음 감사에서 그걸 또 읽으면 같은 수치가 새 문서에서 다시 잡힌다.
업무 하나를 등록하니 문서가 12건에서 13건이 됐다. 제목이 `[수치 감사]` 로 시작하는 글은 감사 대상에서 뺀다.

MCP 를 안 쓰고 REST API 를 고른 이유는 [`docs/flow-api-reference.md`](docs/flow-api-reference.md) 끝에 적어 뒀다.
요약하면 모델에게 도구 선택권을 넘길 자리가 이 구조에 없었고, 응답을 바이트로 봐야 했다.

## 측정이 네 번 틀렸다

채점 버그 4건이 있었고 **네 번 다 모델에 불리한 방향**이었다. 재채점은 저장된 JSON으로 해서 「채점만 바꿨다」가 검증되게 했다.
게이트 임계값도 처음엔 감이었다 — `인용 길이 ≥ 6자` 가 `"참석 5명."`(정당한 인용)을 잘랐다.
값 주변 문맥 3자로 바꾸고 오탐이 사라졌다.

이 저장소가 지켜온 것은 다섯 줄이다.
정답(gold)은 코드보다 먼저 확정한다. 불리한 결과를 지우지 않는다.
확신 등급을 붙인다(실측✅ / 통제🟡 / 추정🟠 / 미재현⬜ / 철회❌).
재현 명령을 숫자 옆에 같이 적는다. 화면 숫자는 저장된 JSON에서 다시 계산한다 — 손으로 옮겨 적지 않는다.

근거 전문은 [`docs/measurement.md`](docs/measurement.md)(라운드 1~3)와 [`docs/measurement-flow.md`](docs/measurement-flow.md)(라운드 4 — 실제 플로우 데이터)에 있다.
원시 결과는 `bench/out/*.json`.

## 직접 눌러 볼 수 있다

읽기만 하는 데모가 아니다.

**게이트 시험** — 인용을 한 글자 고치면 판정이 그 자리에서 뒤집힌다. 모델 호출 0회.
여기서 도는 `checkClaim` 은 서버가 쓰는 그 파일이다. `src/gate.js` 를 빌드 때 `public/lib/` 로 복사하고 복사본은 저장소에 넣지 않는다.
화면용 사본을 따로 두면 화면이 실제 판정과 갈릴 수 있다.

**내 글로 해보기** — 수치가 든 글을 붙여넣으면 추출·게이트·판정이 돈다. 호출 1회.
내 한도를 쓰는 기능이라 입력 길이(4,000자)·같은 IP 간격(20초)·하루 총량(12회)으로 막고, 막힐 때는 사유를 그대로 말한다.
화면에 **남은 횟수를 적는다.** 다만 그 숫자는 Gemini 의 잔여가 아니다 — Gemini 는 남은 횟수를 알려주지 않고, 소진되면 그때 `RESOURCE_EXHAUSTED` 로 알 뿐이다.
적히는 건 **내가 건 가드의 잔여**고, 잔여를 묻는 요청(`GET /api/try`)은 모델을 부르지 않는다.
붙여넣기 모드는 지표 묶기를 코드가 한다(지표명이 같으면 한 그룹). 문서가 하나뿐이라 그 판단이 거의 필요 없고, 그렇게 호출을 2회에서 1회로 줄였다.

**업무로 등록** — 감사 결과가 실제 플로우 업무·하위업무·담당자로 만들어진다.
서버는 클라이언트가 보낸 몸통을 그대로 믿지 않는다. 업무 본문과 **모든 하위업무 본문**에 적힌 인용이
그 프로젝트 원문에 실재하는지 **게이트 ①(인용이 원문에 실재)과 같은 대조로** 다시 확인한 뒤에만 쓴다.
쓰기도 같은 대조를 통과해야 한다.

## 무엇을 어디에 뒀나

전부 읽을 필요는 없다. 이 도구의 주장은 두 파일에 있다 —
[`src/gate.js`](src/gate.js)(인용을 원문에 되짚는 3조건)와 [`src/verdict.js`](src/verdict.js)(코드만으로 가르는 판정).
합쳐 170줄이고, 임계값을 그렇게 잡은 근거와 재현 명령이 주석에 같이 있다.

```
src/
  flow.js      봉투 판정 · 커서 페이징 · 읽기/쓰기 엔드포인트
  gemini.js    스키마 강제 · 재시도 · 일일 한도면 즉시 폴백 · 호출 원문 기록
  collect.js   글+댓글 → 문서. htmlContent 블록 복원 · 시스템 댓글 제외
  extract.js   배치 추출 + 예산 분할 + MAX_TOKENS 대응
  gate.js      인용 게이트 3조건
  cluster.js   지표 묶기(모델) + 참조 게이트(코드)
  verdict.js   판정 — 코드만
  task.js      감사 결과 → 플로우 업무·하위업무·담당자·우선순위
  audit.js     스냅샷 하나로 묶는다
api/
  audit.js     지금 다시 감사한다 (키는 서버에만)
  submit.js    업무 등록. 인용을 원문에 대조한 뒤에만 쓴다
  try.js       붙여넣은 글 감사. 길이·간격·총량으로 막는다
public/        화면. 스냅샷 하나만 읽는다
scripts/       빌드와 로컬 서버 — 배포와 같은 핸들러를 부른다
test/          fetch 를 갈아 끼우고 가짜 클라이언트를 넣는다
bench/         측정 하네스 — 구현에 들어가지 않는다
```

경계가 두 군데다. **모델과 코드 사이** — 지표명을 붙이고 같은 지표끼리 묶는 것은 모델이 하고, 인용 대조와 판정은 코드가 한다.
**읽기와 쓰기 사이** — 읽기는 서버 키로 대신 하고, 쓰기는 검증을 한 번 더 통과해야 한다.

배포는 Vercel이다. 정적 파일은 `public/`, 서버는 `api/` 다.
화면은 저장된 스냅샷을 먼저 그리고 그다음 `/api/audit` 으로 갈아 끼운다. 실패하면 저장된 것을 그대로 두고 사유를 화면에 적는다.
라이브 경로는 모델을 빠른 쪽으로 고정했다 — 상위 체인은 실측 23~105초로 흔들려 함수 상한 60초를 자주 넘겼고, 잘리면 호출만 태우고 결과가 없다.

## 테스트가 잡는 것

`npm test` — 의존성 없이 `node:test` 로 돈다. 건수를 이 문서에 적지 않는다. 테스트를 늘릴 때마다 숫자가 어긋나고, 그건 이 도구가 잡으려는 바로 그 결함이다. 플로우와 Gemini는 `fetch` 를 갈아 끼워 재고, 수집은 가짜 클라이언트를 넣는다.

실측으로 잡은 결함이 회귀 테스트로 고정돼 있다. 블록 융합, 시스템 댓글, 도구가 자기 출력을 다시 읽는 것,
`connectUrl` 유출, 실패가 200으로 오는 것, 일일 한도에서 대기 없이 폴백하는 것.

통과만 하는 테스트인지도 확인했다. 시스템 댓글 필터·게이트 문맥 조건·쓰기 검증을 하나씩 무력화하니 각각 해당 테스트만 실패했다.
일일 한도 폴백을 빼자 테스트는 실패하지 않고 **46초씩 기다리다 멈췄다** — 내가 5분을 태웠던 그 상황이 그대로 재현된다.

## AI가 쓴 코드, 내가 정한 경계

구현의 상당 부분은 Claude로 썼다. 정한 것은 나다 — 게이트를 둘지 말지, 모델에게 무엇을 맡기고 무엇을 코드에 남길지,
불리한 측정을 지울지 남길지, 어디서 멈출지. 이 저장소에서 제일 오래 걸린 일도 코드가 아니라 **판정 규칙의 사정거리를 좁히는 일**이었다.

## 다음에 손댈 곳

**문서 간 정합성으로 넓히는 것.** ADR·설계 문서·ERD·인터페이스 명세처럼 서로를 전제하는 문서들이
어긋난 채 굳는 것이 원래 보려던 문제다. 넓히는 기준은 위와 같다 —
**마지막 한 걸음이 코드로 떨어지는 주장부터**다. 필드 이름·타입·엔드포인트 경로처럼 식별자로 대조되는 것이 그쪽이다.
모델에게 「이 둘이 모순인가」를 묻기 시작하면 게이트는 남아도 지킬 것이 없어진다.
비용은 판정이 아니라 그 앞에 있다 — 주장의 축이 `{값·단위·측정방법}` 에서 `{이름·종류·선언된 곳}` 으로 바뀌어서,
추출 스키마부터 업무 문안까지 한 벌을 더 만들어야 한다.

**단위를 문자열로만 맞춘다.** 2차 판정이 「같은 단위인가」를 볼 때 `unit === unit` 완전 일치를 쓴다.
`ms` 와 `밀리초`, `개` 와 `건` 과 `케이스` 가 갈린다. 실제로 데모에서 `1,284케이스` 와 `1,200여개` 는
지표 묶기가 한 그룹으로 붙여 줬기 때문에 대조가 됐고, 그게 안 됐으면 단위가 달라 서로 못 봤다.
**단위 유사도 비교**가 있으면 묶기가 갈라져도 대조가 산다 — 다만 넓힐수록 다른 지표를 끌어들이니
「어디까지가 같은 단위인가」를 먼저 재야 한다. 지금 규칙이 오탐을 얼마나 내는지도 아직 안 쟀다(아래 참조).

**에디터로 쓴 글에서 재현율을 재는 것.** 지금 데모는 전부 API 로 심어 `htmlContent` 가 비어 있다.
굵게·표가 값을 감싼 문서에서 게이트가 얼마나 깎이는지 모른다.

**2차 판정의 오탐을 재는 것.** 「단위만 같고 다른 지표일 수 있다」고 적어 뒀지만 실제로 재보지 않았다.
타임아웃 `5000ms` 같은 값을 데이터에 심고 오탐이 나는지 보면 된다.

**배치를 키웠을 때 누락을 재는 것.** 12문서에서는 안 났다. 100문서에서 안 난다는 근거가 없다.

**붙여넣기 가드를 공유 저장소로 옮기는 것.** 지금은 인스턴스 메모리라 「하루 12회」가 아니라 「인스턴스당 12회」다.

## 아직 못 잰 것

에디터로 **직접 쓴** 글에 대한 파이프라인 실행은 안 해 봤다. 심은 글은 전부 API로 넣어 `htmlContent` 가 비어 있고,
블록 융합 계측만 에디터 글로 했다. 그 표본도 글 3건이라 13.6%를 비율로 쓰지 않는다.

굵게·표가 값을 감싼 문서에서 재현율이 얼마나 깎이는지 모른다. 게이트가 깨지는 조건(인용 안쪽의 비공백 문자)은 알아냈지만
실제 문서에서 그게 얼마나 흔한지는 안 쟀다.

배치 크기 기준도 12문서 표본에서 나왔다. 100문서에서 같은 비율이 나온다는 근거는 없다.

**묶기가 실행마다 흔들린다.** 같은 입력·같은 모델(`gemini-3.6-flash`)로 두 번 돌렸더니
주장이 24건 / 28건, 지표 그룹이 10개 / 6개로 갈렸다. 한 번은 회의 참석 인원 `5명` 과 스프린트 참여 인원 `3명` 을
한 그룹으로 묶어 **「값이 갈림」 업무를 만들었다** — 다른 것을 센 숫자다. 다른 한 번은 둘 다 안 묶었다.
표본이 실행 두 번이라 비율로 쓰지 않는다. **흔들린다는 것까지만 말한다.**

**이 문제가 얼마나 흔한지도 안 쟀다.** 수치가 어긋난 채 공지로 나가는 일이 팀마다 얼마나 자주 생기는지 모른다.
표본은 나 하나고, 데모 데이터는 내가 썼다. 도구가 그런 문서를 찾아낸다는 것까지가 잰 것이고,
그런 문서가 많다는 것은 안 쟀다.

「내 글로 해보기」의 하루 총량·IP 간격 제한은 **인스턴스 메모리에 있다.** 서버리스는 인스턴스가 여럿이고
콜드스타트마다 초기화되므로 실제로는 「하루 12회」가 아니라 「인스턴스당 12회」다. 진짜 방어선은 Gemini 자체 한도다.
공유 저장소를 두면 정확해지지만 이 규모에 부품을 늘리지 않았다.

라이브 감사는 함수 상한(60초) 때문에 빠른 모델로 돈다. 저장된 스냅샷은 상위 모델로 만든 것이라
**라이브 결과가 저장본보다 덜 뽑히는 경우가 있다.** 배지에 어느 모델이 돌았고 저장본과 몇 건 다른지 적는다.
